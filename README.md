Langfuse 官方介绍包含 LLM 应用观测、提示词管理、评估与数据集等能力。本期聚焦：**记录请求 → 找到问题步骤 → 提出改进假设 → 加入回归评测**。

## 3. 五个需要懂的概念

| 概念 | 含义 | PM 应问的问题 |
| --- | --- | --- |
| Trace | 一次完整请求的链路 | 用户任务完成了吗？ |
| Observation | 请求中的步骤，例如检索、工具调用 | 失败或耗时集中在哪里？ |
| Generation | 模型生成类步骤 | 哪个模型、多少用量、什么成本？ |
| Session | 相关请求组成的交互 | 单轮正常，整段对话是否解决问题？ |
| Score | 针对请求或步骤的评价 | 谁评的、什么规则、覆盖多少样本？ |

一次客服请求可以包含“检索政策”和“生成回答”两个子步骤。并行步骤耗时不能直接相加作为端到端延迟。当前 v4 文档把整体输入、输出放在根 observation 上，旧教程需要核对版本。

来源：[观测概览](https://langfuse.com/docs/observability/overview)、[数据模型](https://langfuse.com/docs/observability/data-model)、[Scores](https://langfuse.com/docs/evaluation/scores/overview)。

## 4. 从观测到产品决策

以下是独立的产品分析方法，不是官方效果承诺。

| 现象 | 先检查 | 可考虑的实验 |
| --- | --- | --- |
| 请求变慢 | 检索、生成、排队、重试各占多少 | 只针对已定位瓶颈改动 |
| 成本上升 | 输入长度、模型、重试、缓存变化 | 按任务及版本拆开比较 |
| 流畅但答错 | 检索依据是否正确，生成是否遵守 | 分开测试检索与生成约束 |
| 用户反复追问 | 前轮未解决，还是继续探索 | 结合 session 人工抽样 |
| 质量分下降 | 用户分布或评分器是否变化 | 固定样本和规则做对照 |

日志提供调查线索，相关性不等于因果。

## 5. 原创练习：用三个合成请求定位问题

无需账号、安装软件或调用模型，即可先完成纸面分析。下面全部为教学构造，不是实际 trace、账单或真实商家政策。

虚构场景：蓝鲸文具店客服。政策为“未拆封商品签收后 7 天内可申请退货”。三个请求都检索到了这份正确政策。

| 用例 | 回答 | 人为设定的生成耗时 | 模拟模型成本 |
| --- | --- | --- | --- |
| normal | 7 天内可申请 | 0.08 秒 | USD 0.0010 |
| slow | 7 天内可申请 | 0.60 秒 | USD 0.0030 |
| wrong | 99 天内可申请 | 0.08 秒 | USD 0.0015 |

### 你的任务

1. 为每条请求画出根请求、检索、生成三层关系，记录政策版本和回答
2. 将 slow 放入性能问题队列，将 wrong 放入质量问题队列
3. 说明 wrong 的证据支持什么、不支持什么
4. 算出每次请求成本与每个成功结果分摊的成本
5. 写出只改变一个变量的下一轮实验
6. 设计一张真实接入时所需的字段表

### 字段表模板

| 字段 | 本练习填写方式 | 目的 |
| --- | --- | --- |
| trace_id / case_id | 虚构唯一标识 | 关联一个完整请求 |
| 步骤名称与父子关系 | 检索政策、生成回答 | 定位发生问题的位置 |
| 应用、Prompt、模型版本 | 模拟值并标注 | 避免把不同版本混在一起 |
| 文档版本与检索输出 | 虚构政策 v1 | 判断是否拿到依据 |
| 输出 | 上表固定文本 | 与依据和评分对应 |
| 用量、成本及计量范围 | 模拟；仅模型成本 | 防止把模拟费用当账单 |
| 评分来源和规则 | 人工核对固定答案 | 说明评分能力边界 |
| synthetic | true | 明确不是生产数据 |

### 参考推理与计算

- wrong 检索正确但回答错误，应先验证生成遵守依据的能力；当前证据不支持“检索坏了”
- 平均延迟会掩盖 slow，也看不出 wrong 快但错误
- 固定答案匹配率为 2/3，约 66.7%
- 总模拟模型成本为 USD 0.0055
- 平均每请求模拟模型成本约 USD 0.00183
- 每个匹配成功结果分摊模拟模型成本为 USD 0.0055 / 2 = **USD 0.00275**

最后一项包含失败请求消耗，但不含检索、人工、基础设施或 Langfuse 服务成本。三个样本不能证明线上质量，不能据此设定生产 p95/p99。

### 练习验收

完成后应能：
- 准确区分慢请求、错误回答和正确检索
- 写清每个指标分母与成本范围
- 说明哪条证据支持下一步实验
- 避免声称合成数据证明真实系统可靠
- 不将固定字符串匹配当作通用事实准确性评分

建议下一轮实验：仅调整生成阶段的依据约束，用固定案例比较正确性、拒答、延迟和成本；保留可能增加无必要拒答的风险。

## 7. 真正上线前，先统一指标口径

| 指标 | 分母或范围 | 常见误读 |
| --- | --- | --- |
| 任务完成率 | 纳入统计的业务任务 | HTTP 200 不等于完成 |
| 质量合格率 | 实际评分样本 | 必须同时报告评分覆盖率 |
| 端到端延迟 | 用户发起至最终返回 | 不等于单次模型耗时 |
| 单成功任务成本 | 总纳入成本 / 成功任务数 | 不能漏掉失败与重试 |
| 观测覆盖率 | 有 trace 的请求 / 应记录请求 | 分母需要独立业务来源 |
| 人工接管率 | 对应流程任务数 | 接管不一定是坏事 |

比较时尽量固定任务类型、样本、评分规则与时间窗口。记录模型、Prompt、应用和评估器版本。手工上报 token 时检查缓存分类是否重叠，避免重复累计。

## 9. 数据、评价和许可限制

### 数据与评价
- trace 可能包含提示词、输出、检索片段和工具参数，应先确定采集范围、查看权限、保留期与删除办法
- [Masking](https://langfuse.com/docs/observability/features/masking)需要按 SDK 与集成核对覆盖，示例正则不是完整隐私方案
- 有 trace 不等于答案正确，有 score 不等于评分可靠
- 未采样或未成功上报的失败可能不在看板中
- 自托管仍需访问控制、备份与数据治理
